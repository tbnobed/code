**Likely cause:** The preview is serving a different copy or a cached version of `index.html`, not the file you edited. A passing smoke check only proves something returns HTTP 200, not that it's your edited file. Nothing in the brief tells us which is true, so verify rather than assume.

**Candidates, most likely first:**
1. **Stale cache**: the browser or preview iframe is caching the page. A hard reload or disabled cache would show it.
2. **Different served file**: the framework serves a copied or built artifact (e.g. `dist/`, `public/`, or a temp dir snapshot made at startup) and not the `index.html` you edited. Or you edited a file in a different working directory than the one the server uses.
3. **Server not restarted or no live-reload**: "Application is running" may be the old process still alive, with the re-run reusing it.
4. **Content mismatch**: the gallery overlay may be rendered or overwritten by JS, or there may be a second copy of that markup elsewhere.

**How to verify (in order):**
- `curl -s http://<host>:<port>/ | grep -n "After\|Paint Refining"` and compare with `grep -n "After" index.html`. If curl shows "After", it's a browser or preview cache problem. If curl shows "Paint Refining", the server is serving another file.
- Check response headers with `curl -I` (look at `Cache-Control`, `ETag`, `Last-Modified`).
- Run `grep -rn "Paint Refining" .` (excluding `node_modules`) to find other copies, such as a build output directory.
- Check the framework's static-root config and the process start time, then fully stop and restart it.

**Smallest fix:** Edit the file in the actual served directory, or restart the server so it re-copies the file, then hard reload.
